# From vibe coding to the dev codebase: shared components and `/slice-vibe`

Date: 2026-10-15. Status: design approved in conversation, spec awaiting review.

## Goal

A product manager prototypes pages with the design system's components in a **vibe repo** (this repo, `mvp-design-system`, the Equipment
Loan Tracker). After the C-level approves a prototype, a developer runs **`/slice-vibe <page>`** in the **dev codebase** to bring the UI
over, and then does the backend and integration. The demo to the PM shows how fast and how cleanly that slice goes, with measured numbers.

The components are the problem to solve: the dev side must have the same components the prototype was built with, and decisions made
about components (a property that Figma no longer has becomes deprecated, `searchable` on Select) must not get lost between the two repos.

## What exists today (facts, from reading the repos)

- `mvp-design-system` (vibe): React 18, rsbuild, Tailwind 3. `src/components/` holds the shared components, each with a `*.stories.js`,
  plus three app-level files without stories (`Layout.js`, `Notifications.js`, `CommandPalette.js`). `src/tokens`, `src/foundations`, the Figma
  sync skill (`.claude/skills/building-storybook-from-figma`, copy in `scripts/figma/`), the review service (`api/review.mjs`, page `/review`) and
  a deployed Storybook (own Vercel project) live here.
- `swt-fe` (the real dev codebase, read only): React 18, rsbuild; **already has Storybook** (37 stories, 76 component folders) and **already has
  slice commands** (`/slice-swt`, `/slice-cmt`, `/slice-figma`, `/sync-figma`, `/sync-swt`) that copy pages from the TRMS prototype into `src/pages/v2/`
  and fix imports, props and colours. Its components have drifted from the prototype's (for example `pagination-v2` has another API than the
  prototype's). It has no token pipeline like this repo's (`src/tokens`, `src/foundations` do not exist there).

## Decision

**The dev codebase owns the components and the Storybook. The vibe repo holds a generated, read-only copy.** (Option B of three: A = Storybook in vibe
and slice copies components to dev; C = a third repo with a design system package.) B can grow into C later by extracting `src/components` into a package.

Why: a review compares the code with Figma and weighs it against the callers (who uses a property). Real callers exist only in the dev codebase,
so the comparison and the decision (remove, deprecate, keep) belong there. The vibe repo follows.

## Design

### 1. The two repos

| | `mvp-dev` (new, the "dev codebase" for the demo) | `mvp-design-system` (vibe, exists) |
|---|---|---|
| Owner | developers | the PM, with Claude Code |
| `src/components/` | **the source**: every folder that has a `*.stories.js` | **generated copy**, never edited by hand |
| Tokens and Foundations | the source (`src/tokens`, `src/foundations`, generated from Figma) | generated copy |
| Storybook | official, deployed | a local view of the copy (`npm run storybook`), not an official one |
| Figma sync skill, review service and page `/review` | here | removed from here (phase 4) |
| Pages, mock data, `Layout`, `Notifications`, `CommandPalette` | the sliced pages | the prototype pages and the app-level files |
| `src/proposed/` | no | new components the PM makes |

Rule for what moves: a component folder **with a `*.stories.js` is design system** and belongs to `mvp-dev`; a file without a story is app-level and stays
in the vibe repo (under `src/app/`). `mvp-dev` is a working name; creating its remote repository is the user's decision and not part of this spec.

### 2. `npm run pull-ui` (in the vibe repo)

Copies from the dev repo into the vibe repo: `src/components/**` (with stories), `.storybook/**`, `src/tokens/**`, `src/foundations/**` and the
files the tokens need (`tailwind.config.js` token wiring, `src/index.css` token import, `src/utils/cn`). The source is a folder (default `../mvp-dev`,
overridable by the env var `UI_SOURCE`); a later version can read an npm package instead, with the same lock file.

It writes `ui-lock.json`: the source commit, and a hash per copied file. `doctor` gets two checks:
- **edited by hand**: a copied file whose hash differs from the lock (names the files);
- **behind**: the dev repo's `HEAD` is newer than the lock (says how many commits and whether any changed a component the vibe pages use).
Both are warnings, not blocks. The copied folders carry a `README` line "generated by pull-ui, do not edit".

The vibe repo's `CLAUDE.md` changes: components come from `pull-ui`; never edit them; to get a component that does not exist, make it in
`src/proposed/` (next section) or ask; deprecated properties (`@deprecated` in the manifest) are not used in new pages.

### 3. New components from the PM: `src/proposed/`

A component the PM needs and the design system lacks is built in `src/proposed/<kebab-name>/index.js` with its story, using tokens and the existing
components. It is used freely in the prototype. `/slice-vibe` lists every `proposed` component a page uses and does **not** move it automatically:
the developer decides to promote it (it becomes a component in `mvp-dev` with a story, checked against Figma by the sync skill) or to replace it with an
existing component.

### 4. `/slice-vibe <page>` (a Claude Code command in `mvp-dev`, `.claude/commands/slice-vibe.md`)

Input: the vibe repo path (default `../mvp-design-system`) and the page name. Steps, each reported:
1. **Version check.** Compare the vibe `ui-lock.json` with the dev `HEAD`. When behind, list the properties and options the page uses that are now
   deprecated or removed. Does not stop; the developer reads it.
2. **Copy** the page and its page-only files (mock data, page components) into `src/pages/<feature>/`; fix the import aliases (same alias names, so mostly nothing).
3. **Scan** the page: imports from `components/proposed`, hand-written `button`/`input`/etc. that Storybook has a component for, hex colours, arbitrary
   Tailwind values, deprecated properties. Report each with file and line; do not silently fix.
4. **Route** added to the app's router; data stays the mock with a `TODO(integration)` marker per call site. Backend and integration are the developer's next task, out of scope.
5. **Verify:** production build, `checkUtilities` on every class in the page, `renderCheck`.
6. **Slice report** (`docs/slices/<page>.md`): start and end time and duration, files copied, the components the page uses (with versions), counts of each
   scan finding, and the verification result. The report is the demo's evidence.

### 5. Review and deprecation stay in the dev repo

The Figma sync, `reviewSync`, the review store, and the page `/review` (designers and product owners) run against `mvp-dev`, where the callers are.
A decision (for example `searchable`: keep as deprecated) changes the component there; the next `pull-ui` carries the `@deprecated` description and the new default
down to the vibe repo, and its components manifest then tells the PM's AI not to use it. The review service contract (`reference/review-service.md`) does not change.

## Demo plan

1. In the vibe repo: the PM asks Claude for a new page (a real feature the C-level discussed; for the demo, one more page of the Loan Tracker) using the pulled components. Show that it uses only Storybook components.
2. "Approved." In `mvp-dev`: `/slice-vibe <page>`. Show the report: duration, files, scan findings (ideally none), build and render check passed.
3. The deprecation point: show `searchable` deprecated in `mvp-dev`, then `pull-ui`, then the vibe manifest marking it deprecated and a new page not using it.
4. The baseline, for a fair comparison: slice the same page against an independent component set (option A: the page's components differ from the dev's), and report how many import, property and colour fixes the scan finds. **No numbers are promised in advance**; the report produces them.

## Out of scope

Backend and integration of the sliced page; migrating the real `swt-fe` (it lacks the token pipeline and needs an adapter, a separate project); publishing an npm package (option C);
preventing hand edits in the copy (a warning only); automatic promotion of proposed components.

## Risks and limits

- A copy can lag or be edited by hand: `doctor` warns, nothing blocks. A PM who edits the copy loses the edit at the next `pull-ui`; the README line and `CLAUDE.md` say so.
- Moving the review service to `mvp-dev` (phase 4) needs a new deployment and moving its environment variables; the current deployment keeps working until then.
- The real `swt-fe` Storybook has 37 stories against this design system's components; the demo uses a clean repo, so it does not prove the same result on `swt-fe`.
- The dev repo is new and has no history or real callers; the review's caller counts in the demo come from its own sample pages.

## Phases (each gets its own implementation plan)

1. **Split.** Create `mvp-dev` from this repo (components with stories, tokens, Foundations, `.storybook`, the skill, the review service and `/review`, `api/`, a minimal app shell and a couple of sample pages for caller counts). Exit: its Storybook builds with 0 errors.
2. **`pull-ui` + lock + `doctor` checks + vibe `CLAUDE.md`.** Exit: the vibe repo builds and renders with the copied components; editing one copied file makes `doctor` warn.
3. **`/slice-vibe` + the report.** Exit: a real prototype page is sliced into `mvp-dev`, builds, and the report is written.
4. **Move the review service** to `mvp-dev`'s deployment and remove it from the vibe repo. Exit: `/review` works from `mvp-dev`; the vibe repo no longer has `api/review.mjs`.
5. **Demo script and the baseline run** (the numbers).
